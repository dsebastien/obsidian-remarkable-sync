# 2026-09-21: Stop automatic sync re-downloading notebooks that never changed

## The report

Notebooks untouched for months were being pulled down and rewritten repeatedly, with automatic
sync enabled at a 240 minute interval on Android. The settings copy promised to "periodically sync
all notebooks that need updating", so the question was what "needs updating" actually meant.

## Root cause

One conceptual error with two opposite symptoms: **the code compared a local wall clock against a
cloud timestamp.**

`deriveSyncStatus` tested `lastSyncedAt >= lastModifiedCloud`. `lastSyncedAt` is `Date.now()` on
the device; `lastModifiedCloud` came from reMarkable's servers. Two unrelated clocks.

1. **It never noticed a real edit.** Both values are written in the same `updateState` call, and
   the cloud timestamp is necessarily older than the `Date.now()` written beside it. So after any
   successful sync the comparison was permanently true. A notebook edited on the device stayed
   "synced" forever. Neither call site passed the notebook's CURRENT cloud timestamp, though both
   had it in scope.
2. **It re-downloaded everything whenever state was lost.** With no state, a notebook is
   `never-synced` and gets pulled. State was being erased by `pruneMissing`, which treats "absent
   from the listing" as "deleted on the device" and was fed by a `listDocuments` that returned `[]`
   on _every_ failure path. So "the cloud is unreachable" and "you have no notebooks" were the same
   value, and a network blip erased sync state for some or all notebooks.

Four paths returned `[]`: root hash fetch failure, root index fetch failure, a `catch` around the
whole function, and `Promise.allSettled` plus `continue`, which silently dropped individual
documents whose metadata failed.

Latent since `6cb55d8` (0.1.0, 2026-03-07), which shipped both the wall-clock comparison and the
`[]`-on-failure listing. Became destructive in 1.10.0 (2026-07-29), when `7eef6ec` added pruning
and `3ee0110` added the timer that repeats it unattended. Neither commit is wrong alone; the defect
is in the seam, and the prune commit's "absent means deleted" assumption was never checked against
the listing function's actual failure behaviour.

The panel refresh prunes through the identical path, so opening the sidebar while offline wiped the
store on its own. Turning automatic sync off would not have made a user safe.

## Fixes

- **`deriveSyncStatus(state, cloudLastModified)`** compares the cloud's current timestamp against
  the one recorded at the last sync. Like against like. `lastSyncedAt` is now display only.
- **`parseCloudTimestamp`** parses strictly. `parseInt` accepts anything starting with a digit, so
  an ISO-8601 `lastModified` would have parsed as `2026`, compared as 1970, and made every notebook
  look permanently up to date. The pipeline records `0` for an unknown timestamp rather than
  `Date.now()`, which would have stored a value the cloud never issued.
- **`DocumentListing`** replaces the bare array. `complete` gates pruning; `error` is what the UI
  shows. Changing the return type forced all five call sites to be revisited, which is the point.
- **Pruning is gated on `complete`** in both the auto-sync service and the panel.
- **Failures are visible.** The panel shows a banner and keeps the last known list rather than
  blanking. The two commands said "No notebooks found" when the cloud was unreachable; they now
  report the real error.
- **`describeListing` / `failedListing`** extracted as pure functions so the rule that authorises
  destructive pruning is testable without a live cloud. There was no spec for the cloud service at
  all, which is why this survived eight weeks.

No migration. `lastModifiedCloud` already stores exactly what the new comparison wants.

## Expected behaviour

| Situation                      | Before                                | After                              |
| ------------------------------ | ------------------------------------- | ---------------------------------- |
| Notebook you never touch       | Re-pulled whenever a listing hiccuped | Synced once, never again           |
| You edit it on the device      | **Never re-synced**                   | Marked needs-sync, pulled next run |
| You only open it on the device | Re-pulled                             | Re-pulled, no vault file changes   |
| Deleted on the device          | State pruned, files kept              | Unchanged                          |
| Network failure mid-listing    | Whole sync store wiped                | Nothing pruned                     |
| Partial listing                | That notebook re-pulled forever       | Shown and syncable, nothing pruned |
| Panel opened while offline     | Wiped the store                       | No-op, banner shown                |

Two consequences on upgrade, both expected:

1. Notebooks edited on the device since their last sync have been silently stale and will correctly
   flip to `needs-sync`. One burst of real work, not a regression.
2. A store already wiped by the old behaviour means one full re-sync, then it settles. The
   skip-if-unchanged write guard makes that bandwidth, not file churn.

and confirm untouched notebooks are not re-downloaded.

## Known, not fixed

1. **Opening a notebook on the device still causes a re-download.** reMarkable bumps `lastModified`
   for benign reasons. Output is deterministic and the write guard skips identical bytes, so no
   vault file changes, but the transfer still happens. The exact fix is to store the document's
   index hash (already cached in `entryHashMap`) and compare content rather than timestamps.
   Deferred: it needs a sync-store schema field and a migration.
2. **`listDocuments` still has no direct spec.** The rule that gates pruning was extracted and is
   covered, but the network plumbing around it is not.
