# 2026-08-01

## PDF support plan written

Plan: `documentation/plans/pdf-export.md`. No code yet. Three phases: notebook to PDF export,
syncing PDF-backed documents, annotation burn-in.

Scoping went through two rounds. The user first asked for **notebook to PDF export** only, then
asked whether that would also produce the reMarkable PDF with annotations on top. It would not, and
phase 1 alone would arguably make PDF-backed documents worse by wrapping blank ink-only pages in
something that looks like a real document. User then chose **full burn-in, phased**.

Audited the pipeline to answer two questions the user asked directly:

- **Is there PDF export today?** No. `renderPage()` encodes to PNG/JPEG/WebP only and
  `writePageImage()` writes one file per page.
- **Is there annotation-over-PDF today?** No. `downloadDocument()` does fetch the `<id>.pdf` blob
  (it downloads every entry in the document index), but `parseDocument()` only reads `.metadata`,
  `.content` and `.rm`, so the PDF is dropped. A PDF-backed document syncs as ink on blank white
  pages, or reports "No pages with content found" if it was never annotated.

## pdf-lib measured, not estimated

An earlier draft of the plan recommended hand-rolling a minimal PDF 1.4 writer and taking no
dependency, on an estimate of ~380 KB for pdf-lib. That recommendation does not survive burn-in:
modifying an existing PDF means walking its page tree, which means parsing cross-reference streams
and object streams, which is a real PDF reader rather than a small serializer.

First measured with esbuild (Bun was not installed yet), then **re-measured under Bun 1.3.14's own
bundler** with the exact production settings from `scripts/build.ts`:

| Entry point exercised                          | Bundled  | `require()` | Reviewer flags |
| ---------------------------------------------- | -------- | ----------- | -------------- |
| baseline, empty module                         | 0.6 KB   | none        | none           |
| `PDFDocument.load` + `save`                    | 505.3 KB | none        | none           |
| `create` + `embedJpg` + `drawImage`/`drawLine` | 505.5 KB | none        | none           |

Bun agrees with esbuild to within 5 KB. Tree-shaking buys nothing: the module graph eagerly pulls
the 14 standard-font AFM tables (~180 KB), UPNG and pako regardless of what is imported, and
Obsidian's single `main.js` means a lazy `import()` cannot defer the cost.

Two corrections to earlier numbers in this session: the estimate of ~380 KB was wrong (it is ~505
KB), and the ~129 KB current-bundle figure taken from an earlier history entry was stale. The
measured production bundle today is **145,385 bytes**, so pdf-lib takes it to roughly 650 KB, about
4.5x rather than 5x.

Clean on every applicable rule: zero `require(...)`, no `new Worker`, no `createObjectURL`, no
`createElement("script")`. pdf-lib ships `main: cjs/index.js` and `module: es/index.js` with no
`browser` field, and since neither entry touches Node builtins the `fflate/browser` precedent does
not apply.

User accepted the size, so pdf-lib is in and the hand-rolled writer is out. One PDF path, not two.
Recorded as a deliberate documented exception to the small-dependency guidance in `AGENTS.md`,
taken because correctness on arbitrary user PDFs (encrypted, linearized, hybrid-reference) beats the
bytes. Still outstanding: the same build under the reviewer's older Bun (observed 1.2.14), and a
`dist/main.js` audit once pdf-lib is wired in for real rather than probed in isolation.

Other design call: **new `savePdf` boolean** rather than adding `'pdf'` to `imageFormat`, which
drives both the canvas encoder and the file extension.

Settings shape settled with the user: PDF export is a **"Save as PDF" toggle in its own "PDF"
settings section** (`settings/components/pdf-section.ts`), independent of `saveImages`. The
alternative considered first was folding both into an `outputFormat: 'images' | 'pdf' | 'both' |
'none'` enum, which needed a load-time migration of `saveImages: false` and left a "Save images"
toggle sitting next to a dropdown that also offered "Images". Two independent booleans cover the
same four states, need no migration, and match the existing component-per-heading settings pattern.

Open decisions still listed for the user: how an exported PDF should represent blank pages and pages
that failed to render, since dropping them silently shifts every later page number.

## Sync churn, raised by the user

Concern: generated PDFs rewriting on every run and churning vault sync, especially with automatic
sync on. Two independent causes, both addressed in the plan.

**pdf-lib metadata.** It stamps `/CreationDate`, `/ModDate` and `/Producer` by default. Measured on
1.17.1, hashing two runs a second apart:

| Path                                     | Two runs           |
| ---------------------------------------- | ------------------ |
| `create()` default                       | differ             |
| `create({ updateMetadata: false })`      | **byte-identical** |
| `load()` default                         | differ             |
| `load(bytes, { updateMetadata: false })` | **byte-identical** |

`updateMetadata: false` beats pinning the dates to a fixed epoch: `create()` then emits no
CreationDate, ModDate, Producer or `/ID` at all. On the burn-in load path it also preserves the
**source document's own** metadata rather than restamping it (verified via the getters after a
round trip: Title, Author and a 2020 creation date all survived). Left on, pdf-lib overwrites
`/Producer` and bumps `/ModDate`.

**Unconditional writes.** Deterministic bytes do not help on their own, because `writePageImage()`
calls `vault.modifyBinary()` whenever the file exists, so identical content still bumps the mtime
and still reads as a change to Obsidian Sync, Git or Dropbox. Auto-sync only processes
`needs-sync`/`never-synced` notebooks, but a device can bump `lastModified` for benign reasons such
as opening a notebook, which re-runs the pipeline over unchanged content. Plan adds a
skip-if-unchanged guard (compare length then bytes, skip the write on a match) applied to
**images as well as PDFs**, since loose images have the same problem today.

1 0 0 -1 0 1651.42747 cm             y-flip, as the plan derived independently

## Full review, and a real bug it caught

User asked for a full end-to-end review. Found one genuine defect, shipped in the commits above and
missed by all 287 tests.

### BUG: `savePdf` silently reset on every restart

`loadSettings()` in `plugin.ts` merged `data.json` over the defaults using a **hand-written list of
`if (loaded.x !== undefined) draft.x = loaded.x` assignments**. `savePdf` was added to
`PluginSettings` and `DEFAULT_SETTINGS` but not to that list, so it saved correctly
(`saveSettings` spreads the whole object) and then fell back to `false` on the next launch. The user
would enable PDF export, restart Obsidian, and find it off with no error anywhere.

Not caught because nothing exercised `loadSettings` at all.

Fixed structurally rather than by adding the missing line: extracted `mergeLoadedSettings()` into
`settings/load-settings.ts`, driven by `Object.keys(DEFAULT_SETTINGS)` so a setting cannot be
forgotten again. It also now ignores values whose type does not match the default (a hand-edited or
corrupt `data.json` degrades to defaults instead of poisoning the plugin) and still copies only keys
present in the defaults, so `tokens` cannot leak into `PluginSettings`.

`load-settings.spec.ts` includes a loop asserting **every** key in `DEFAULT_SETTINGS` survives a
round trip, which would have failed against the old code and will catch the next such omission.

### End-to-end matrix in headless Chrome

Real `renderPage` (OffscreenCanvas), real `buildPdf` (pdf-lib), real `writeBinaryIfChanged` against
an in-memory vault. Built with a Bun plugin that stubs `obsidian`, so the production code path runs
unmodified.

| Case                        | Result                                                           |
| --------------------------- | ---------------------------------------------------------------- |
| images only                 | 2 images, no PDF                                                 |
| PDF only                    | `Work/Notebook.pdf`, no images                                   |
| both                        | 2 images + 1 PDF                                                 |
| neither                     | nothing written, 0 failures                                      |

The churn result is the notable one: it proves JPEG encoding through `OffscreenCanvas` is
deterministic in practice, which the whole skip-if-unchanged guard depends on.

### BUG: highlighter strokes rendered as opaque black bars

`STROKE_COLOR_MAP` covered colours 0-8, but firmware emits 0-13 (rmscene's `PenColor` is the
reference). `stroke-renderer` falls back to black for unmapped colours, and **colour 9 is the v2
highlighter's own colour**, so a 105px-wide highlighter painted a solid black bar over the writing
it was highlighting. Plainly visible in the first render of the real notebook.

Pre-existing, and it affects the existing **image** output too, not just the new PDF export. Fixed
by adding 9-13. Colours 10-13 use rmc's palette; 9 is a default, since the device stores the exact
highlight colour per notebook as an ARGB code in `.content` `extraMetadata`
(`LastHighlighterv2ColorCode`, observed as `0xFFFFED75` = rgb(255,237,117)), which the renderer does
not read yet. Worth a follow-up for full fidelity.

## Phases 2 and 3 built

Source-backed documents now keep their original and get an annotated copy. Built together because
the pieces are interdependent.

**Phase 2.** `parseDocument` keeps the source blob on `Notebook.sourceDocument` and stamps each page
with `sourcePageIndex` from `cPages[i].redir.value`. Device-inserted pages have no `redir` and get
no index, so their ink is never guessed onto page 0. A source-backed page with no `.rm` layer no
longer logs a warning, since an un-annotated page of a real document is normal.

**Phase 3.** `output/pdf-coordinates.ts` holds the transform as pure functions with 16 specs,
including the real-export landmark and the out-of-sample highlighter as regression tests.
`output/pdf-annotator.service.ts` loads with `updateMetadata: false`, draws each layer onto its
mapped page, and refuses encrypted or oversized sources rather than mangling them.

`document-output.service` now branches: a source-backed document writes the original through and an
annotated copy beside it, and **never** assembles page images into a PDF, which is the defect that
started all this.

Verified end to end through the shipped code on the real sample document:

```
sourceDocument: pdf, 829848 bytes    sourcePageIndexes: [0]
19 strokes, 661 points, 326 ms
created: sample-document.pdf, sample-document (annotated).pdf
```

3 pages kept, title "Sample Document" preserved, 684 vector ops on page 0 of which 60 are
the translucent highlighter, original text still selectable. The arrow points at "a known
heading" and the highlight covers the intended paragraph.

## Rule conflict found for phase 2

The existing rule skips pages with no strokes. For a PDF-backed document a stroke-free page is not
blank, it is an un-annotated page of a real book, and skipping it would delete content. The rule
must be scoped to notebook pages. This is an amendment to `Business Rules.md`, not an optional
decision.
