## Issue #28 — listing fans out unbounded, drops documents, writes to the wrong folder

Re-checked against 2.1.0: all three defects still present, plus a fourth found while reading the
callers.

| #   | defect                                                                                                                                                                                | consequence                                                                                                                         |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `listDocuments` mapped every root entry into `Promise.allSettled`, two sequential requests each                                                                                       | 500 items = 1,000 requests at once, on every auto-sync tick and panel refresh                                                       |
| 2   | `fetchBlob` collapsed every non-401 failure to `null`, no 429 branch, no `Retry-After`, no retry                                                                                      | rate limits looked like missing blobs                                                                                               |
| 3   | `listDocuments` skipped entries whose metadata came back null and returned the rest as a success; `buildFolderPath` broke out of the walk on a missing folder and returned the prefix | a transient failure on one folder wrote that folder's notebooks to the wrong vault folder; the next sync wrote them again elsewhere |
| 4   | `listDocuments` returned `[]` on any error, and both callers then ran `pruneMissing([])`                                                                                              | one failed listing wiped the whole sync state, so the next run re-processed every notebook                                          |

### Fix (branch `fix/listing-resilience`)

- `src/utils/concurrency.ts` — `mapWithConcurrency`: bounded worker pool, results in input order,
  first rejection stops new work and is rethrown.
- `src/app/services/cloud/http-retry.ts` — `requestWithRetry` + `SyncRequestError`. Retries 429,
  5xx and network errors; honours `Retry-After` (seconds or HTTP-date, capped 30 s), else
  backoff 500 ms to 8 s, 4 attempts. Other statuses terminal. Errors carry `status`, `retryable`,
  `attempts`. `requestUrl` is called with `throw: false` so the 429 response headers are readable.
- `sync-protocol.ts` — `fetchRootHash` and `fetchBlob` go through the retry loop and **throw**
  instead of returning null. The index named the blob, so a blob that cannot be fetched is a
  failed request, never an absent file.
- `remarkable-cloud.service.ts` — `listDocuments` either returns the complete listing or throws
  `RemarkableCloudError`. Metadata fetched 6 at a time; the first failure aborts. Genuinely absent
  or unparseable metadata is skipped with a warning (a retry cannot change the index). Folder
  path resolution is a pure function (`resolveFolderPath`) returning resolved / trashed /
  unresolved; unresolved fails the listing naming the notebook and folder id; trashed at any
  depth excludes the notebook (before, only a direct `trash` parent did). Deleted folders keep
  their name so a document still pointing at one resolves to its real path. Metadata is cached
  by entry hash across listings, bounded to the entries in the last root index. The transport
  (`fetchRootHash`/`fetchBlob`) is injectable for tests.
- `downloadDocument` — 6 files at a time; any failed file fails the document (before, a missing
  page blob produced a document with that page silently gone).
- Panel — failed refresh keeps the previous list, shows a Notice with the reason, prunes nothing.
  Auto-sync already caught the error; it no longer prunes on failure because nothing is returned
  to prune against.

### Not changed, deliberately

- The concurrency limit is a constant (6), not a setting. Nobody has asked for a knob and the
  right value is a property of reMarkable's rate limiting, not of the user.
- Whether reMarkable answers with 429, 5xx or dropped connections under load is still not
  observed (the issue reporter could not confirm either). All three are retried the same way.
- `IndexEntry.subfiles` is still read nowhere (noted in #37 for the asset folder question).

### Verification

`tsc`, `lint --max-warnings 0`, `rules:check`, `build` clean. 581 tests, 46 new across
`concurrency.spec.ts`, `http-retry.spec.ts` and a new `remarkable-cloud.service.spec.ts` with an
in-memory sync service (root index, per-entry index and metadata blobs, scriptable failures,
in-flight counter). No live-account run: the 429 path is exercised only through scripted
responses. Manual check worth doing on a large account: refresh the panel and watch the network
tab for at most 6 concurrent `/files/` requests and for the second refresh fetching only the root
index.
