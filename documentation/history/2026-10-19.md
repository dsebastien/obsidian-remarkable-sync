# 2026-10-19: #47 follow-up, three symptoms and a plan

## Accomplished

- Re-read #47 with the reporter's screenshots and settings (reMarkable 2, plugin 2.4.0, PDFs uploaded through the official desktop app). The report is three separate symptoms. Plan written: `documentation/plans/troubleshooting-and-diagnostics.md`.
- Symptom 1, original written but no `(annotated)` copy: reproduced with owner-password PDFs (RC4 and AES, empty user password, the library-database case). pdf-lib 1.17.1 refuses them, the plugin writes the original, shows "could not annotate" and then "Processed N pages". `@cantoo/pdf-lib` 2.11.1 (MIT, same API) decrypts them with `password: ''`, verified in a scratch test including render of the saved page. Not yet adopted.
- Symptom 2, yellow text highlights drawn as black bars: root cause found on real Paper Pro files, after a first best-guess commit. A text highlight made with a palette colour (yellow 3, green 4, pink 5, grey 8) carries the ARGB tag as a placeholder `000000ff`; only an id-9 highlight carries its real colour. The parser took the placeholder as "opaque black". `highlightColour` and `highlightOpacity` now use the ARGB only when the id is 9 (`hasOwnHighlightColour`, mirroring strokes), and palette ids map to the device's own highlighter colours (`HIGHLIGHT_PALETTE`, values from rmscene's corpus). The luminance fallback stays as a last defence. The parser also warns when a GlyphRange has no colour tag and defaults it to id 9 instead of 0.
- Symptom 1 fixed: `pdf-lib` replaced by `@cantoo/pdf-lib` 2.11.1, loaded with `password: ''`. Owner-locked PDFs (empty user password) annotate; a file that needs a real password reports `needs-password`. Failures carry a reason and each gets its own notice. The source's encryption dictionary is dropped from the object graph so pdf-lib-based readers do not misread the output as encrypted. Fixtures: five qpdf-locked PDFs embedded as base64 (`fixtures/locked-pdfs.ts`), since specs may import neither `node:fs` nor a `Bun` global. The fork imports bare `fflate`, whose Node entry would pull `worker_threads` into the bundle and break mobile; `scripts/build.ts` redirects it to `fflate/browser` (`BROWSER_ENTRY_PACKAGES`, pinned by `build.spec.ts`). ADR 0002.
- Live test on the user's own account: six generated PDFs under `obsidian-remarkable-sync` (unlocked control, RC4-40, RC4-128, AES-128, AES-256 owner-only, AES-256 with a reader password). With 2.4.0, the owner-locked file reproduced the reporter's console output exactly. With the branch, the real device files annotate (17 strokes, 6 text highlights on the RC4-128 document). The branch's production build is installed in the vault as `1.6.0-test` for the re-sync.
- Observation to explain: the Paper Pro opened and text-highlighted the reader-password PDF (the cloud copy is byte-identical to the locked file, and its text highlights carry the document's real text). The plugin cannot decrypt it without the password and reports `needs-password`.
- Symptom 3, folders of ink-only JPEGs: expected after a reinstall (defaults `saveImages: true`, `savePdf: false`; page images never contain the source). Docs line pending, defaults decision goes to the maintainer as a separate issue plus ADR.
- Format 1 theory from 2026-10-06 does not apply to this reporter (official app uploads are format 2). The fix stays, it is real for rmapi-style uploads.
- Test material: six generated PDFs (unlocked control, RC4-40, RC4-128, AES-128, AES-256 owner-only, AES-256 with a reader password) for upload to the test account under `obsidian-remarkable-sync/issues/47`.

- The parser spec gained a `buildGlyphItemData` builder so text highlight blocks can be constructed in tests.
