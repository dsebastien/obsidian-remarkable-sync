# 2026-07-19

## PA triage routing for idle handwritten pages (GP-125)

Feedback: "route new pages that have no live activity in last 1h to the pa
agent just like voice notes." Built entirely in this plugin (the ticket's
"prefer extending rmobs" hint was stale — `rmobs` is push-outbox only; this
plugin owns pull + OCR, confirmed against `~/.gp/docs/projects/tool-remarkable-sync.md`
"Direction update (2026-06-27)" and `~/.gp/docs/projects/tool-obsidian-remarkable-sync.md`).

### Changes

- `PageOcrState` gains `routedSrcHash?` / `routedAt?` (`domain/sync-state.ts`);
  `NotebookSyncState` gains `visibleName?` / `folderPath?` (provenance, set on
  every `updateState` call from `notebook-pipeline.service.ts`).
- New pure selector `selectPagesToRoute(store, now, idleMs)`
  (`domain/triage-routing.ts`, +spec): a page routes when it has been OCR'd,
  its notebook's persisted cloud `lastModifiedCloud` is `>= idleMs` old, and
  it has not already been routed for its current `srcHash`. Idle time is
  measured from the cloud-stamped mtime (not "when we first observed it"), so
  a backlog notebook OCR'd today but last edited a week ago routes
  immediately rather than waiting another hour. The pipeline already holds
  `lastModifiedCloud` back to its prior value until every OCR-enabled page
  succeeds, so a partially-OCR'd notebook is never mistaken for idle-and-done.
- New pure payload builder `buildTriagePayload` + `triageNoteId`
  (`domain/triage-payload.ts`, +spec): produces the exact md_capture
  triage-queue JSON shape (`{chat_id, text, source, note_id}` — see
  `main.go` `routeViaTriage`), embedding the page's OCR markdown, notebook/
  page provenance, and the saved page-image's vault-relative path.
- New writer `writeTriageRequest` (`services/triage/triage-queue.service.ts`,
  +spec): Node `fs`, atomic `.tmp` + rename into the queue dir, matching
  `routeViaTriage`'s own publish so the 5s `process_triage_queue.sh` poller
  never reads a half-written file.
- New orchestrator `routeIdlePages` (`commands/route-idle-pages.ts`, +spec):
  groups candidates by notebook, reads each notebook's assembled markdown
  once, extracts the page's block via `parseManagedBlocks`, writes the queue
  file, then calls the new `syncStoreService.markPageRouted` (a targeted
  single-page write — never touches other pages' state). A page whose block
  isn't found/hash-mismatched (write race) is left un-routed and retried next
  cycle; never marked routed without a confirmed write.
- Hooked into `syncAllNotebooks`'s `finally` block (not inside the
  needs-sync branch — an idle notebook has a stable cloud mtime and would
  never re-enter `processNotebook`), so it runs after every sync-all pass
  (startup, interval, manual) **even when nothing needed syncing** — that's
  exactly the case where a previously-synced-but-not-yet-idle page becomes
  eligible with no new sync to trigger it. Wrapped in try/catch, fail-soft,
  never throws into the sync loop.
- Settings: `triageEnabled` (default **on**), `triageIdleMinutes` (default 60),
  `triageQueueDir` (default `~/Vaults/personal/triage-queue`), `triageChatId`
  (default `-5188649683`, the PA chat — matches md_capture's `TRIAGE_CHAT_ID`).
  New "PA triage routing (GP-125)" settings section.

### Decisions

- Dedup key is `srcHash` (the existing rendered-page content hash) per page —
  "content hash" per the ticket. A later edit advances `srcHash`, making the
  page eligible again automatically; no separate version counter needed.
- No batching: a notebook with several newly-idle pages files one triage
  request per page (matches "dedup by page id + content hash" literally;
  each request is small and the queue/poller are already per-item).
- `remarkable-web` "routed" status display: out of scope for this change —
  the sync store already carries `routedSrcHash`/`routedAt` if a later change
  wants to surface it; no dashboard edit made here.
