# 2026-07-30

## Issue #13 — mobile support: evaluation

Audited what actually blocks Obsidian mobile. Already mobile-safe: all HTTP goes through `requestUrl`, vault writes via `vault.createBinary`, binary parsing via `DataView` (no `Buffer`), pages render sequentially (no fan-out memory spike).

Two real blockers found:

1. **Token storage** — `token-store.ts` was the only Node-dependent module (`node:fs`/`os`/`path`), writing `~/.remarkable-sync/token.json`. Nothing outside the vault is writable on mobile. **Addressed in this session.**
2. **Bundled Node builtins** — a top-level `import` of a Node builtin is hoisted by the bundler into a top-level `require("node:fs")`, which runs at `main.js` evaluation and throws on mobile, preventing the plugin from loading at all. Verified empirically with isolated `bun build` runs: static import → `var import_node_fs = require("node:fs")` at top level; function-scoped `require` → stays inside the function body. Now a business rule.

Still open before `isDesktopOnly` can be flipped (**none self-verifiable — no live vault, no device**):

- `OffscreenCanvas` + `convertToBlob` on iOS WKWebView (needs iOS 16.4+); Android WebView is fine. No fallback exists today.
- `crypto.randomUUID()` in `remarkable-auth.service.ts` — secure-context gated, unconfirmed on iOS.
- `.rmdoc` file picker (`accept=".rmdoc"`) — iOS may not resolve the unknown extension and show no selectable files.
- **New finding:** JSZip is bundled through `target: 'node'`, so the bundle contains `require("buffer"/"stream"/"util"/"events")`. They sit inside lazy CommonJS wrappers (not hoisted), but they will be evaluated when JSZip actually runs — likely breaking `.rmdoc` import on mobile. Needs a browser-targeted JSZip resolution before the flip.
- Battery/data: auto-sync intervals plus 1404×1872 canvases over cellular want a mobile-specific guard.

## Token storage moved to `data.json` (prerequisite for #13)

Decision (user): `data.json` becomes the storage for all platforms, with a backwards-compatible desktop import so **existing users never have to reconnect**.

- Tokens live under the `tokens` key in `data.json`, deliberately **outside `PluginSettings`** — the settings object is written to the debug log on every load/save (`plugin.ts`) and users paste it into bug reports.
- `plugin.persistData(patch)` is now the only permitted `data.json` writer. `saveData` replaces the whole file, so the previous `saveData(this.settings)` would have erased the tokens on the next settings change. Writes merge into the last known contents and are serialized.
- Legacy `~/.remarkable-sync/token.json` is imported once per vault on first read and **never deleted automatically** — it is machine-global and shared by every vault, so deleting it after one vault migrated would silently disconnect the others. Explicit removal offered in the settings tab.
- `legacyTokensImported` marker in `data.json` bounds the import to once per vault. Without it, disconnect would be undone by a re-import on the next read.
- Node builtins are now loaded via a function-scoped `require` behind `Platform.isDesktopApp`.
- Behaviour change: **tokens are per-vault, not per-machine**. Existing multi-vault users are covered (each vault imports the same file), but a new pairing no longer propagates across vaults.

Files: `token-store.ts` (rewritten), `plugin.ts` (`persistData`/`getDataValue`/`rawData`), `utils/plugin-data.ts` (new: `mergePluginData`, `createWriteQueue`), `remarkable-auth.service.ts`, `commands/disconnect-device.ts`, `settings/components/auth-section.ts`.

## Defects found by review (codex gpt-5.6-sol, high effort) and fixed

Two rounds. All confirmed fixed in round two; round one's five findings did not recur.

1. **Import marker written before the tokens** — a failed second write left the marker set with no tokens, permanently skipping a still-valid legacy file. Fixed by collapsing to a single atomic write (`TokenStatePatch`); a failed import is now retried on the next read.
2. **In-flight refresh resurrected tokens after disconnect** — fixed with an `authGeneration` counter captured on _function entry_ (the first attempt captured it too late, after the initial network call) and re-checked after every await preceding a mutation; a write that lands after a disconnect is undone via `tokenStore.clear()`.
3. **`clear()` swallowed write failures** — disconnect reported success while tokens remained on disk, so the next launch came back connected. `clear()` now throws; `disconnect-device.ts` reports the failure instead of claiming success.
4. **Poisoned write queue** — chaining only on the fulfilled path left `persistQueue` permanently rejected after one `saveData` failure, silently skipping every later write. Extracted to `createWriteQueue()`, which continues from a settled state. `rawData` is now updated only after the write lands.
5. **Legacy removal button could delete the only copy** — it appeared whenever the file existed, including when the import had failed. Now gated on the `legacyTokensImported` marker, which is written atomically with the tokens.

Declined (with reason): the reviewer flagged the **Remove** button as violating "never delete". The rule is _never delete automatically_; this is an explicit, clearly-labelled user action. Also declined: marking the import done when the legacy file is _absent_ — it would add a spurious `data.json` write on every fresh mobile install, and re-importing a file that reappears (i.e. the user ran an old version again) is defensible.

## After 1.13.0 — mobile blockers investigated

Plan written: `documentation/plans/mobile-support.md`.

### JSZip / Node builtins — FIXED, replaced with fflate

Two fixes tested and rejected first:

- **`target: 'browser'` globally: unsafe.** Bun silently rewrites `require('node:fs')` to an empty-object stub `(()=>({}))`. `loadNodeModules()` would return that stub (its `try/catch` passes), then fail inside `readLegacyTokenFile`, whose own `catch` returns null — so the legacy token import would silently never run and **existing desktop users would be logged out on upgrade, with no error anywhere**. Also grew the bundle 129 KB → 226 KB.
- **Aliasing `jszip` → `dist/jszip.min.js`: functionally correct but reintroduces a review warning.** Verified identical behaviour on a generated zip (same entry list and byte lengths through the exact `loadAsync` → `entry.async('arraybuffer')` path the import service uses), removes every `require()` from the bundle, and is ~30 KB smaller. But the prebuilt dist _inlines_ the `setimmediate` polyfill including its old-IE `document.createElement("script")` branch, which `stripSetImmediatePolyfillPlugin` can no longer reach (it matches the module path `/setimmediate/setImmediate.js`). That would undo the "dynamic script element creation" fix from 2026-07-29.

**Done:** replaced JSZip with `fflate`, imported as **`fflate/browser`**. fflate's default (`node`) entry has the same trap — it starts with a top-level `require("module")` + `worker_threads`. Uses `unzipSync`; the async variant pulls in worker machinery (`new Worker` over a blob URL) that the reviewer flags. `.rmdoc` files hold a single notebook, so inflating inline is cheap.

Verified:

- Byte-identical extraction vs JSZip on an archive written by Python's `zipfile` (mixed deflate/stored entries, explicit directory entry) — same keys, same bytes.
- `dist/main.js` now has no `require()` beyond `obsidian` and the three guarded desktop-only Node builtins, and zero `createElement("script")` / `new Worker` / `createObjectURL`.
- Builds cleanly under the reviewer's Bun 1.2.14 with identical output (the `fflate/browser` subpath export resolves fine in the old bundler).
- fflate's bundled footprint is ~6 KB vs JSZip's ~128 KB for the same operations (measured in isolation).

`stripSetImmediatePolyfillPlugin` deleted from `scripts/build.ts` — nothing pulls `setimmediate` any more, so the plugin was dead code. New spec `rmdoc-import.service.spec.ts` with a committed fixture at `src/app/services/import/__fixtures__/sample.rmdoc`; `extractRmdocFiles` is now exported and synchronous.

### `crypto.randomUUID()` made defensive (unreleased)

Was evaluated at module load in `remarkable-auth.service.ts`. Only exposed in secure contexts, so on a non-qualifying webview it would have thrown during `onload` and stopped the plugin loading entirely. Now `utils/uuid.ts#generateUuidV4`, called lazily on first registration, with `crypto.getRandomValues` and then `Math.random` fallbacks. Not security sensitive (device identifier only). 5 specs. Removes the device dependency from that blocker.

## isDesktopOnly flipped to false — experimental mobile release

Decision (user): ship mobile support unverified and let users report from real devices, rather than block on hardware we do not have.

Desktop-regression confidence before flipping (the user's condition):

- `.rmdoc` extraction verified against **four independent zip writers/shapes** by sha256: Python `zipfile` deflate, zip64, a **streamed archive with data descriptors** (written to a non-seekable stream — the most plausible real-world difference), and Info-ZIP CLI (unicode filenames, empty file, nested dirs). All exact matches. Earlier: byte-identical vs JSZip.
- `crypto.randomUUID` path is unchanged on desktop (the API exists there).
- No real `.rmdoc` export was available to test, so that remains the residual risk.

Also added: `isPageRenderingSupported()` gates both the sync pipeline and .rmdoc import. Without it a device lacking `OffscreenCanvas` (iOS < 16.4) reports only "N pages failed to render", which makes bug reports useless; it now names the requirement. Auto-sync already defaults to off, which covers the battery/data concern without new code.

`import/no-nodejs-modules` activated on the flip (it is conditioned on `isDesktopOnly`). Resolved properly rather than blanket-disabled: specs and `test-setup.ts` are exempted in `eslint.config.ts` (never bundled), and the three lazy requires in `token-store.ts` carry a scoped `eslint-disable` with a reason.
