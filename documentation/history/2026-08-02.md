# 2026-08-02

## Done

Work on two rendering gaps, on `feat/pdf-export`. **Uncommitted and unverified**: the commits were
reset after review, because rendering changes were being declared correct on the strength of an
agent looking at a PNG. See `plans/match-remarkable-export.md` for how this is meant to go instead.

**Textured pens.** `speed`, `direction` and `pressure` were parsed for every point and used by
nothing. `segmentColour` in `domain/pen-model.ts` now fades each brush and tilt-pencil segment
toward the page by rmc's intensity curve. Both renderers resolve colour per segment instead of once
per stroke, so the grain survives.

**Highlighter snapping.** New `services/output/pdf-text-lines.ts` recovers a page's text bands from
its content stream, and a stroke that is genuinely a line swipe is drawn as one rectangle per line
it crosses. No glyphs are decoded: only the positioning operators are tracked, which needs no font
tables.

The first cut snapped any wash stroke that passed near text, which was wrong: it straightened
circled words and fluid shading into bands nobody drew. `snapPathToLines` now decides from the path
itself (mostly on text, horizontal, each line visited once, staying on the line) and returns null
for everything else, which falls back to the raw path. 1 of 5 wash strokes on the sample snaps.

**Wash pens composite multiply.** Found while checking the snapped output. A v2 highlighter records
ARGB alpha 255, so drawing it as ordinary coverage painted an opaque bar over the words it marked.
Highlighter and shader strokes and text-selection annotations now use `BlendMode.Multiply`. That in
turn forced unsnapped wash strokes to be drawn as a single SVG path rather than one line per point
pair, because a multiply blend composites per drawing operation and a segmented stroke multiplied
itself at every overlap, which darkens the ink past its recorded colour and leaves the round caps
visible along the path.

## Decisions

**Everything about a text line is measured per line, never per document.** The sample page alone
carries three band heights (12, 18, 36pt) and four different baseline gaps, so a page-wide constant
would already be wrong inside one page. Band height comes from each line's own font size scaled by
the text matrix, and the slack for matching a stroke to a line is proportional to that line's own
height rather than a fixed number of points.

**Rotated pages are not snapped.** A content stream's lines are bands of constant y in user space,
which only matches what the reader sees at `/Rotate` 0. At 90 or 270 a band would cross the text
instead of following it, so those pages fall back to the raw path.

**Snapping never loses ink.** Unreadable content, no text on the page, or no line near the stroke
all return false and fall back to drawing the raw path.

## Verification

**None of the rendering changes are verified.** tsc, lint and 413 tests are clean, and none of that
says anything about how a page looks.

Measured on the sample, and nothing more: 36 text lines recovered from the page content stream;
band heights of 12, 18 and 36pt with four distinct baseline gaps on that one page; 1 of 5 wash
strokes accepted by the geometric test, the other 4 falling back to the raw path.

Whether any of it renders correctly is for a human to judge against reMarkable's own export. See
