# 2026-07-16

## Fix: malformed token file bricked plugin load ("Could not load the plugin")

### Root cause (customer report)

Customer reported "Could not load the plugin 'remarkable-syncronizer'" persisting across uninstall/reinstall. Diagnosis:

- `onload` (plugin.ts) awaited `authService.isAuthenticated()` with no try/catch.
- `isAuthenticated()` → `hasValidTokens()` → `tokens.deviceToken.length`, where `readTokens()` blindly cast `JSON.parse(content) as StoredTokens`.
- A `~/.remarkable-sync/token.json` containing valid JSON of the wrong shape (e.g. `{}`, missing/non-string `deviceToken`) threw a TypeError → `onload` rejected → Obsidian reports "Failed to load plugin".
- The token file lives outside the vault, so uninstall/reinstall never cleared it — matching the customer's symptoms exactly.

Note: invalid JSON (truncated file) was already handled (caught → null). Only valid-JSON-wrong-shape crashed.

### Changes

- `token-store.ts`: new exported `parseStoredTokens(content)` — validates JSON + exact shape (string `deviceToken`/`userToken`, number `userTokenExpiry`), returns `null` on any mismatch. `readTokens()` now uses it and logs a warning on malformed files.
- `token-store.ts`: `writeTokens()` now writes atomically (temp file + `renameSync`) so an interrupted daily token refresh can't leave a mangled `token.json`.
- `plugin.ts`: `isAuthenticated()` call in `onload` wrapped in try/catch → falls back to `isConnected = false` (belt-and-braces; auth failures must never prevent plugin load).
- New `token-store.spec.ts` covering `parseStoredTokens` (valid, extra props, invalid JSON, non-object JSON, empty object, missing fields, wrong types). 143 tests pass.
- Business rule added: plugin load must never fail because of token file contents.

### Customer workaround (pre-fix versions)

Delete `~/.remarkable-sync/` and reconnect. Docs (`docs/tips.md`) already mention manual token file deletion.

### Verification
