# 2026-09-13

## Issue #36 — capture tool images not recognised (reMarkable OS 3.27+)

Report: "The plugin does not recognize the images captured by ReMarkable's new feature: the
capture tool." Reporter attached `Chemistry notes.rmdoc` (3 pages, one capture each).

### Reproduced

Against the unmodified parser: 2 of the 3 pages vanished.

| page | content              | old behaviour                                   |
| ---- | -------------------- | ----------------------------------------------- |
| 0    | 82 strokes + capture | rendered, capture missing, handwriting survived |
| 1, 2 | capture only         | dropped as blank, never reached the vault       |

The capture-only case is the worse one: a 3-page notebook lands as a 1-page note with no error.

### Format findings

The archive gained a per-page asset folder, `<documentId>/<pageId>/<imageId>.png`, and two .rm
block types the parser did not know:

- **`0x0e` SceneImageInfoBlock.** `tag 1 Length4` holds a varuint count followed by one `tag 0`
  subblock per declaration: 16 raw id bytes, an LWW file name at index 1, LWW flags at index 2
  (observed `[17, 0]`, unused).
- **`0x0f` SceneImageItemBlock.** Same CRDT envelope as `SceneLineItemBlock`, scene item type
  **7 = Image**. Carries an LWW asset reference, a vertex buffer of four `(x, y, u, v)` float32
  vertices, and triangle indices `0,1,2,2,3,0`.

Placement rectangles cross-check exactly against the PNGs, which is what confirmed the vertex
layout was read correctly rather than coincidentally:

| page | PNG       | PNG aspect | parsed rect aspect |
| ---- | --------- | ---------- | ------------------ |
| 0    | 769 x 836 | 0.9198     | 0.9199             |
| 1    | 440 x 465 | 0.9462     | 0.9462             |
| 2    | 490 x 511 | 0.9589     | 0.9589             |

Cross-checked against rmscene's open PRs (ricklupton/rmscene#52 and #51), which cover the same
blocks and date the feature to firmware **3.27**. That comparison caught two real bugs: the byte
after the tag-1 subblock header is a **varuint count of declarations**, not an opaque kind byte
(every sample page has exactly one capture, so the wrong reading produced the right answer by
luck and would have dropped every capture after the first on a multi-image page); and the asset
file name is not necessarily `.png`.

### Adversarial review

Five specialists plus a tribunal over the branch diff. Four defects survived verification, none
of them catchable by the repo's definition of done, because the renderer had almost no coverage.

1. **One bad image block discarded the rest of the page.** `parseBlock` sought to the block
   boundary only on the success path, so a throw escaped to `parseRmFile`, whose catch broke out
   of the block loop. The info block sits at index 4 of every page file, ahead of all 82 strokes,
   so an unexpected field in a block we only started reading would take the page's whole
   handwriting with it. Fixed with a `finally`, which also protects stroke, text and highlight
   blocks.
2. **The extension allowlist decided which assets existed.** An unlisted extension resolved to no
   data, which made a capture-only page look blank and deleted it: issue #36 reintroduced by its
   own fix. Removed; the .rm file is the authorization. This also settled a three-way
   disagreement, one side of which wanted PNG-only for decoder-surface reasons. That argument was
   defeated by its own evidence, since `createImageBitmap` sniffs container magic and ignores the
   Blob type, so the extension list never bounded decoder surface at all.
3. **A capture that would not decode was written as a successful page.** Now counts what reached
   the canvas and returns null when nothing did. A page with typed text or highlights keeps its
   blank ink layer, which is correct for it.
4. **Placement rectangles sized the canvas with no ceiling.** The dangerous case is the middle of
   the range: roughly 8000x16000 stays under Blink's cap, so it allocates about half a gigabyte
   successfully and then blocks the main thread. Implausible placements are ignored and logged.

Worth recording why the obvious structural fix was wrong. Three places test `image.data !== null`
and a specialist proposed single-sourcing them. The tribunal showed that would close nothing: the
three sites do not disagree, the shared test is simply the wrong test, and two of them run where
decodability cannot be evaluated. They carry cross-references to each other instead.

Hardening in the same pass: file names read as UTF-8 rather than windows-1252 (`TextDecoder('ascii')`
is a WHATWG label for windows-1252); the asset id read structurally at the LWW value index rather
than by scanning for the first 16-byte field; a short or non-whole vertex buffer rejected rather
than yielding a plausible wrong rectangle; a rotated or cropped placement reported; per-placement
logging bounded to one line plus a summary; all subblock reads routed through one bounded reader.

### Rebased onto current main

The branch was first cut from a stale local `main` that was 62 commits behind, which would have
shipped a 1.15.0-era plugin. Redone from `origin/main` (2.0.0 era) and the change re-applied onto
the current architecture rather than replayed commit by commit, because upstream had rewritten the
same files.

Adaptations the new base required:

- `Page.images` is **optional**, matching `highlights?` / `text?`. The pre-rebase version made it
  required, which no longer fits the convention.
- `parseBlock` returns the upstream `{ stroke?, highlight?, text? }` shape, extended with
  `imageAssets?` and `placement?`, rather than a discriminated union.
- `renderPageToCanvas` had gained a deliberate blank-canvas path for typed-only pages. The
  blank-page fix had to not break it, so `pageHasContent` was split and the renderer asks
  `pageHasNonImageContent` before deciding a page drew nothing.
- Specs use `Reflect.deleteProperty` rather than `@ts-expect-error`, which the repo's rule gate
  now refuses in staged source.
- `imageAssetMediaType` lives in `image-utils`, where it is a decoding hint rather than a gate.

### Verified

`tsc`, `lint --max-warnings 0`, `rules:check`, 535 tests and `build` all clean.

Rendering cannot run under `bun test` (no `OffscreenCanvas`), so the real parser and renderer were
bundled for the browser and the reporter's file run through them in Chrome. All three pages render
at 1404x1872. Pages 1 and 2 are byte-identical to the pre-rebase render; page 0 differs because
upstream rewrote `stroke-renderer.ts`, not because of anything here.

The new specs were mutation-checked rather than assumed: restoring `break`-on-error fails exactly
the two block-recovery tests and nothing else.

**Still needs manual runtime verification in a real vault.** The browser harness covers parsing,
bounds and drawing, but not Obsidian's write path or mobile. Check: a capture-only page produces a
page image, a mixed page shows both layers, and iOS/Android still render.

### Device

The sample is from a reMarkable 2 class device: `.content` records 1404 x 1872, and the image
quads sit inside the ±702 half-width that implies. Upstream's `device-screen.ts` names that
resolution "reMarkable 1, reMarkable 2, Paper Pure"; Paper Pro is 1620 x 2160.

### Open

- Rotated or cropped placements draw upright and uncropped. The uv pairs are parsed and the
  parser warns, but the renderer still uses a bounding box. No rotated sample exists.
- The cloud sync path has never been exercised for assets. All verification is through .rmdoc
  import. `IndexEntry.subfiles` is parsed but read nowhere, so if the v3 index nests the per-page
  asset folder instead of listing it flat, assets will not download and capture-only pages will
  still vanish. Check against a live account before announcing the fix.
- The per-declaration flags (`[17, 0]` in every sample) are parsed past and ignored.
- These gaps are duplicated in `documentation/Domain Model.md` under `PageImage`, which is where
  they will still be found once this file is no longer the most recent history entry.
