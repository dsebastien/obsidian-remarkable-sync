# 2026-09-30: Schema 4 index regression (#44, #45)

## Accomplished

- #44 / #45: since 2.2.0, accounts on sync schema 4 showed "1 item(s) could not be read" and every download failed (`Failed to fetch blob 0: 400`). Cause: `parseIndexDetailed` skipped a numeric second header line (schema 3 count) but read schema 4's info line `0:{. or docId}:{count}:{size}` as an entry with hash `0`. 2.1.0 had the same misparse but ignored the failed fetch; 2.2.0's strictness (unreadable entry makes a listing incomplete, missing blob fails the download) turned it into a hard failure.
- Fix: the line right after the schema version is a header when it is numeric or matches `^0:[^:]+:\d+:\d+$`. Format confirmed against rmapi-js `src/raw.ts` (reader and writer: `.` for the root, the document id for a document index).
- Tests: parser (root and document info lines, info-shaped line past the header stays an entry) and service level (`FakeCloud.schema = 4`, listing complete and download succeeds, blob `0` never fetched). All fail on the old parser.

## Decisions

- Info line count is not checked against the entries, same reasoning as the schema 3 count (see 2026-09-28).
