# 2026-08-01

## PDF support plan written

Plan: `documentation/plans/pdf-export.md`. No code yet. Three phases: notebook to PDF export,
syncing PDF-backed documents, annotation burn-in.

Scoping went through two rounds. The user first asked for **notebook to PDF export** only, then
asked whether that would also produce the reMarkable PDF with annotations on top. It would not, and
phase 1 alone would arguably make PDF-backed documents worse by wrapping blank ink-only pages in
something that looks like a real document. User then chose **full burn-in, phased**.

Audited the pipeline to answer two questions the user asked directly:

- **Is there PDF export today?** No. `renderPage()` encodes to PNG/JPEG/WebP only and
  `writePageImage()` writes one file per page.
- **Is there annotation-over-PDF today?** No. `downloadDocument()` does fetch the `<id>.pdf` blob
  (it downloads every entry in the document index), but `parseDocument()` only reads `.metadata`,
  `.content` and `.rm`, so the PDF is dropped. A PDF-backed document syncs as ink on blank white
  pages, or reports "No pages with content found" if it was never annotated.

## pdf-lib measured, not estimated

An earlier draft of the plan recommended hand-rolling a minimal PDF 1.4 writer and taking no
dependency, on an estimate of ~380 KB for pdf-lib. That recommendation does not survive burn-in:
modifying an existing PDF means walking its page tree, which means parsing cross-reference streams
and object streams, which is a real PDF reader rather than a small serializer.

Measured pdf-lib 1.17.1 with esbuild using the same shape as `scripts/build.ts`
(`--bundle --format=cjs --platform=node --minify`):

| Entry point exercised            | Minified |
| -------------------------------- | -------- |
| `PDFDocument.load` + `save` only | 500.2 KB |
| plus `pushOperators`             | 500.3 KB |
| plus `drawSvgPath`               | 500.3 KB |

Tree-shaking buys nothing. The module graph eagerly pulls the 14 standard-font AFM tables (~180 KB),
UPNG and pako regardless of what is imported, and Obsidian's single `main.js` means a lazy
`import()` cannot defer the cost. So the real number is ~500 KB against a ~129 KB bundle, about 5x,
not the ~380 KB first quoted.

Clean on the mobile rule: **zero `require(...)` in the bundled output**, so no Node builtins, and no
worker or blob-URL machinery. pdf-lib ships `main: cjs/index.js` and `module: es/index.js` with no
`browser` field, and since neither entry touches Node builtins the `fflate/browser` precedent does
not apply.

User accepted the size, so pdf-lib is in and the hand-rolled writer is out. One PDF path, not two.
Recorded as a deliberate documented exception to the small-dependency guidance in `AGENTS.md`,
taken because correctness on arbitrary user PDFs (encrypted, linearized, hybrid-reference) beats the
bytes. Measurement used esbuild because Bun is not installed here, so it must be re-confirmed under
Bun and under the reviewer's pinned Bun 1.2.14.

Other design call: **new `savePdf` boolean** rather than adding `'pdf'` to `imageFormat`, which
drives both the canvas encoder and the file extension.

Settings shape settled with the user: PDF export is a **"Save as PDF" toggle in its own "PDF"
settings section** (`settings/components/pdf-section.ts`), independent of `saveImages`. The
alternative considered first was folding both into an `outputFormat: 'images' | 'pdf' | 'both' |
'none'` enum, which needed a load-time migration of `saveImages: false` and left a "Save images"
toggle sitting next to a dropdown that also offered "Images". Two independent booleans cover the
same four states, need no migration, and match the existing component-per-heading settings pattern.

Open decisions still listed for the user: how an exported PDF should represent blank pages and pages
that failed to render, since dropping them silently shifts every later page number.

## Two blockers recorded

- **No real fixture.** `sample.rmdoc` is synthetic and holds no PDF-backed document, so nothing in
  the repo exercises a genuine reMarkable export. This is now the largest risk in the plan: the
  phase 3 coordinate mapping (.rm space is x-centred with y downward, PDF space is bottom-left with
  y upward, plus `/CropBox` versus `/MediaBox`, `/Rotate`, and the device's fit scale) cannot be
  confirmed from first principles. Asked the user for a real `.rmdoc` export of an annotated PDF.
- **Bun is not installed on this machine.** `bun` is not on `PATH`, so none of `bun run tsc`,
  `bun run lint`, `bun test` or `bun run build` can run here, and the definition of done requires
  all four. Needs installing before implementation starts.

## Rule conflict found for phase 2

The existing rule skips pages with no strokes. For a PDF-backed document a stroke-free page is not
blank, it is an un-annotated page of a real book, and skipping it would delete content. The rule
must be scoped to notebook pages. This is an amendment to `Business Rules.md`, not an optional
decision.
